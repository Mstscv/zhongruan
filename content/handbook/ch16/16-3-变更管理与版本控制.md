# 变更管理与版本控制

> 零基础导读：需求一变再变，代码被随手改来改去，版本就乱了。这一节讲清"变更怎么走流程、CCB 管什么、版本号和分支怎么用"，是防止项目失控的操作手册。

## 1. 概念与要点

**变更管理**是对变更请求进行识别、评估、批准、实施和验证的系统化过程。变更来源很多：外部环境变化、需求理解偏差、新技术出现、执行中发现问题等。无论原因是什么，影响基线的变更都必须走流程。

**变更管理完整流程**：**提出变更申请 → 影响分析 → CCB 批准 → 实施变更 → 验证变更 → 发布 → 归档收尾**。

- **变更申请**：书面提出变更请求，说明变更内容与理由。
- **影响分析**：评估对范围、进度、成本、质量、风险的影响，为 CCB 决策提供依据。
- **CCB 批准**：**变更控制委员会**（Configuration Control Board）审查并批准或否决。CCB 只审批变更，**不代替项目经理决策**日常事务；项目经理也不能绕过 CCB 擅自批准重大变更。
- **实施、验证、发布**：批准后由项目团队实施，验证结果符合要求后发布到产品库。
- **归档收尾**：登记变更全过程、更新配置状态、归档相关文档，保证可追溯。

**紧急变更**可先实施以控制影响，但必须**事后补办**变更申请和 CCB 审批手续，并记入配置状态报告，不得永久免审。

**基线变更**必须走变更控制：已纳入基线的配置项即使只改笔误，也要申请、批准、按版本规则升版后再纳入，不得直接覆盖或擅自撤出基线。

**版本控制**管理配置项的演变历史，核心机制有三：**版本号**（标识内容差异）、**分支**（Branch，在不影响主线的前提下并行开发、修复或试验）、**标签**（Tag，标记重要节点的版本快照，便于回溯）。分支开发完成后应**合并**回主干，主干按规则升版并打标签。

**文档的版本标记**与代码一致：小的修订次版本号加 1（1.0 升为 1.1）或按修改状态追加修订号（1.0 升为 1.01）；结构性重大改写升主版本号且次版本归 0（1.x 升为 2.0）。

## 2. 关键考点

> 💡 **关键考点**：
> 1. 变更流程七步的顺序：申请、影响分析、批准、实施、验证、发布、归档。先分析后决策，批准后才实施。
> 2. CCB 的角色：审批变更的决策机构，不代替项目经理管日常，也不亲自写代码。
> 3. 紧急变更与基线变更：紧急可先做后补手续；基线变更一律走变更控制，补丁也要走。

## 3. 常见考法

- 给变更流程步骤打乱，选正确顺序；或问"CCB 批准后下一步做什么"。
- 考查 CCB 与项目经理的职责边界：谁能批变更、谁管日常。
- 给"直接改基线代码导致版本混乱"情景，问违反了什么、如何补救。
- 版本号推演：正式版 2.1 小改一次 → 2.11；大改 → 3.0；分支合并后主干升版。
- 紧急变更处置：能不能免审批、要不要补手续、要不要记入状态报告。

常见坑：以为项目经理可自行批准所有变更；以为紧急变更永久免审；把分支当成标签；小改后直接跳主版本号。

## 4. 速记
